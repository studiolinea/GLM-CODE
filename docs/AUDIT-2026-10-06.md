## Veille cloud : configuration à préparer avant activation

Le Mac peut être éteint : le gestionnaire `scheduled` travaille côté Cloudflare. **La veille n'est pas actuellement activée.** Le fichier `wrangler.jsonc` ne contient ni déclencheur cron ni binding AI supplémentaire. Le code seul ne rend pas le service H24 actif.

1. Relire puis appliquer `supabase/07-assistant-veille.sql` sur une base de test. Vérifier les droits avec deux utilisateurs, les écritures interdites et la concurrence du RPC avant production. Le SQL n'a pas été exécuté lors de cet audit.
2. Ajouter le secret serveur `SUPABASE_CLE_SERVEUR` dans le Worker, jamais dans une variable `VITE_…`. Conserver `CLE_CHIFFREMENT` et les secrets des connecteurs côté serveur. Chaque traitement vérifie le propriétaire et l'autorisation de veille du business malgré les droits service_role.
3. Choisir **un** fournisseur dont le compte est effectivement sur le plan Free, sans facturation ni repli payant. Définir `IA_ACTIVEE=oui`, `IA_PLAN_VERIFIE=free` et le mode choisi. Ces déclarations doivent refléter le compte réel ; le code ne peut pas vérifier son contrat de facturation.
   - Cloudflare : `IA_MODE=cloudflare-gratuit`, binding `"ai": { "binding": "AI" }`. Modèle fixé : `@cf/meta/llama-3.1-8b-instruct-fp8`.
   - Groq : `IA_MODE=groq-gratuit`, secret `IA_CLE`, `IA_TRANSFERT_AUTORISE=oui` après acceptation du transfert vers Groq. Endpoint et modèle fixes : `https://api.groq.com/openai/v1/chat/completions`, `openai/gpt-oss-120b`. Pas de fallback Cloudflare ou fournisseur arbitraire.
4. Tester le Worker et mesurer son CPU : le plan Workers Free limite le CPU à 10 ms par invocation. Le chiffre réel n'a pas été mesuré ici. Les lectures sont plafonnées à 45 sous-requêtes et les délais bornés ; une source volumineuse peut donc interrompre un passage sans remplacer le dernier résultat.
5. Pour une version validée, configurer `"triggers": { "crons": ["* * * * *"] }` et `VEILLE_ACTIVEE=oui`, puis activer chaque business dans l'interface. Un passage traite au maximum un business ; la réservation vise une nouvelle lecture après 15 minutes, mais la file, les quotas et les erreurs peuvent allonger ce délai, notamment avec 15–20 business.

Le RPC réserve atomiquement au maximum **40 analyses par jour pour l'ensemble du compte et 4 par business**, demandes manuelles et veille cumulées. La journée de quota est UTC ; l'affichage métier reste Paris. Une empreinte des données utiles évite les analyses identiques. Les quotas fournisseur s'appliquent en plus : Cloudflare Free annonce 10 000 neurones/jour, Groq publie des limites par modèle et organisation à vérifier dans le compte. Les erreurs ou quotas empêchent l'inférence, sans repli payant. Le plafond applicatif ne remplace pas la vérification du plan fournisseur.

## Test du modèle Groq

Un essai réel de `openai/gpt-oss-120b` a été réalisé dans le navigateur Groq Playground, sur le compte Free confirmé à 0 $, avec trois cas synthétiques regroupés dans une requête. Les quotas attendus ont été confirmés dans le compte. Aucune clé API n'a été créée, aucun réglage n'a été changé, aucune donnée privée n'a été envoyée. Ce test est un essai Playground, **pas un test API automatisé ni une validation de l'intégration Pilotage**.

| Cas synthétique | Résultat observé | Limite |
|---|---|---|
| Frais inconnus | Pas de gain inventé | L'état « gains inconnus » n'est pas assez explicitement formulé. |
| Vente remboursée | Ventes nettes 0 €, mouvements −3 € | Le modèle annonce qu'aucune donnée n'est inconnue, puis demande de vérifier les frais : réponse incohérente. Ce cas ne prouve pas que Pilotage sait déterminer un gain après remboursement. |
| Avant lancement | Conseils à budget nul, sans promesse de revenus | Conseils génériques, prototype papier peu adapté au parcours numérique visé. |

**Le conseiller autonome n'est pas validé.** Un seul appel et trois situations ne suffisent pas à mesurer sa fiabilité. Les prochaines évaluations doivent examiner la cohérence, les données manquantes et l'adéquation aux besoins, avec un échec explicite lorsque le modèle invente une certitude.

Dans ce compte, Global ZDR et Inference ZDR sont désactivés ; une rétention pouvant aller jusqu'à 30 jours est possible. Avant tout test API avec données métier ou intégration en production, vérifier et accepter les modalités de rétention/transfert, puis configurer la clé dans un environnement sécurisé, jamais dans la conversation ni le navigateur applicatif. La connexion au Playground ne fournit pas une clé au Worker.

Les calculs déterministes restent la source des chiffres et des preuves : `gainsCentimes` vaut `null` avec frais manquants ou remboursement Stripe insuffisamment modélisé ; les coûts publicitaires/autres dépenses sont transmis comme inconnus ; couverture et fraîcheur sont explicites. Le prompt demande de distinguer faits, données manquantes et hypothèses. Le texte du modèle est affiché comme conseil à vérifier, ne modifie aucun total et ne nourrit pas les constats déterministes. Ces protections réduisent le risque sans garantir qu'un modèle obéira.

Aucune clé Groq n'est disponible dans l'environnement de ce travail : **aucun appel API réel n'a été effectué**. Le script `scripts/tester-groq.mjs` propose un essai synthétique séparé, non équivalent à une validation de bout en bout. Il refuse les appels sans `GROQ_PLAN_VERIFIE=free` et `GROQ_API_KEY`. Les tests automatisés du backend simulent le fournisseur et vérifient les contrats, pas son intelligence.

## Limites à connaître

- L'authentification de récupération est testée via adaptateurs ; aucun email réel ni lien expiré réel n'a été essayé.
- Les synchronisations de données ne sont pas des transactions globales. Après échec partiel, on relit l'état effectivement confirmé et on signale le problème.
- Les remboursements partiels et leur date économique ne sont pas complètement modélisés. Les gains restent inconnus lorsque les frais nécessaires manquent.
- Les vues vidéo sont des compteurs cumulés connus, pas les vues acquises pendant une période. Les ventes observées après une vidéo sont une corrélation, sans attribution prouvée.
- Instagram automatique, pixels, paniers abandonnés et performances publicitaires ne sont pas disponibles sans les sources correspondantes.
- La sécurité effective de Supabase, des comptes fournisseurs et du déploiement nécessite des vérifications dans ces environnements. La relecture du code ne constitue pas une certification de production.
